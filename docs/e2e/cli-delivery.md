# 普通 CLI 与订单交付用例

返回 [E2E 用例总结](README.md)。本页详细说明 6 个注册用例。步骤和检查来自当前测试源码；实际运行状态见总览链接的历史实现记录，本次整理未重新执行。

<a id="case-01"></a>
## 1. 购物车修复

**设计依据与合理性：**[D01：编码工具、作用域指令与调用策略](../implemented/design-evidence.md#d01)。基线真实失败、修复后独立复跑通过且测试源码不变，支持读改测与项目指令设计。

注册测试名：`cart repair: follow workspace instructions, change TypeScript and run its tests`

源码：[cli.test.ts](../../tests/e2e/cli.test.ts)。

- **初始任务：**`cartTotal` 忽略商品数量，并把折扣写成加价。工作区提供三个业务测试和 AGENTS.md，要求只改实现、实际运行测试，并在回复中包含随机项目代号。
- **执行步骤：**宿主先运行业务测试确认基线失败；从构建后的真实 CLI 请求模型修复；Agent 读取、编辑并运行测试；宿主结束后独立重跑同一业务测试。
- **实际检查：**CLI 成功退出并产生 `completed`；独立业务测试通过；测试源码未被修改；回复包含 AGENTS.md 中的项目代号；事件中确实出现成功执行业务测试的 shell 调用。业务值为小计 4095 分、九折后取整 3686 分、空购物车为 0。
- **证明范围与边界：**证明这个短任务能遵循项目说明、修改生产代码并实际验证；有测试完整性和独立复验约束。它只有一个小模块，不能单独证明多阶段或大工程能力。

<a id="case-02"></a>
## 2. 普通会话跨进程恢复

**设计依据与合理性：**[D03：权威会话与持久输入交接](../implemented/design-evidence.md#d03)。随机编号未保存在工作区，两进程交付迫使模型依靠持久历史，检验会话上下文恢复。

注册测试名：`session resume: remember a prior stdin task across separate CLI processes`

源码：[cli.test.ts](../../tests/e2e/cli.test.ts)。

- **初始任务：**空工作区。第一条 stdin 输入包含随机交付编号，要求只记住，不调用工具、不写文件。
- **执行步骤：**第一 CLI 进程结束；第二进程使用相同 session ID 和会话目录，要求把上一条输入的编号写入 `delivery.json`。两个进程均带 `--no-shell`。
- **实际检查：**两次 CLI 都成功完成；第一进程结束后工作区仍为空；第二进程的 JSON 使用原始随机编号并包含 `status: ready`。
- **证明范围与边界：**编号只能从会话历史恢复，因而证明普通会话持久化、跨进程上下文和写文件链路。没有上下文压力或压缩，也没有持久任务控制；`--no-shell` 的使用本身不单独证明一次主动 shell 越权尝试被拒绝。

<a id="case-03"></a>
## 3. 只读库存审查

**设计依据与合理性：**[D01：编码工具、作用域指令与调用策略](../implemented/design-evidence.md#d01)。独立核对库存文件与新增文件，检验只读任务实际没有副作用；本例不要求模型主动发出越权调用。

注册测试名：`readonly review: report out-of-stock items without modifying the workspace`

源码：[cli.test.ts](../../tests/e2e/cli.test.ts)。

- **初始任务：**库存文件中有一个随机 SKU 库存为 0，另一个商品有库存。用户要求报告缺货 SKU，并尝试保存审查文件；权限不允许时直接回复。
- **执行步骤：**从真实 CLI 以 `--readonly` 启动，让模型读取库存并完成审查；宿主随后检查回复和工作区。
- **实际检查：**CLI 成功完成；回复包含真正缺货的随机 SKU；工作区仍只有原库存文件，内容完全相同。
- **证明范围与边界：**证明该审查任务在只读策略下可完成且没有文件副作用。测试不要求模型必须发出一次写调用，也不证明宿主 shell 或文件系统具有操作系统沙箱。

## 4. 单次执行片段轮次预算

**设计依据与合理性：**[D08：累计资源准入与独立额度](../implemented/design-evidence.md#d08)。需要下一轮的读取任务在 turn 上限非成功退出，检验单 Run 额度；累计请求由其他例另验。

注册测试名：`turn budget: exit unsuccessfully when a task requires another model turn`

源码：[cli.test.ts](../../tests/e2e/cli.test.ts)。

- **初始任务：**文件里有随机包裹编号，用户要求先通过 read 读取，再根据工具结果报告，不允许猜测。
- **执行步骤：**真实 CLI 使用 `--readonly --max-turns 1`。设计通过“读取工具 → 下一模型轮次处理结果”触发单次 Run 的轮次限制。
- **实际检查：**CLI 退出码为 1，公开结束状态为 `budget_exhausted`；该测试的直接断言聚焦结束状态，没有额外断言 read 必须实际发生。
- **证明范围与边界：**证明单次 Run 的轮次耗尽按失败公开。它不验证跨阶段、恢复、摘要或重规划共用的累计模型请求预算，也不验证 token / 费用预算。

## 订单任务共用环境与验收者

以下 LT-01 / LT-02 使用同一 [orderFixture](../../tests/e2e/order-fixture.ts)，初始问题为：

| 文件 | 初始问题 | 要实现的行为 |
| --- | --- | --- |
| `src/parse.mts` | 直接按逗号切分；缺少数量、价格与表头校验 | CSV 引号、转义双引号、中文和 CRLF；合法数量与整数分金额；非法输入拒绝 |
| `src/calculate.mts` | 小计按数量计算，但忽略折扣，折扣恒为 0 | 汇总、按订单 ID 排序、折扣向下取整到分、保留商品信息 |
| `src/cli.mts` | 只打印 TODO | 读取 CSV，处理折扣参数，创建目录，导出 JSON；非法输入非零退出且没有成功文件 |

宿主定义三个阶段：M1 解析 → M2 金额计算 → M3 CLI 集成交付。两者都包含 M3；M3 的职责是连接前两个模块并检验实际 CLI。

验收者有三层职责：

1. **E2E 宿主**预先生成 `control/verify.mjs` 和任务合同，固定正确业务结果。Agent 可读需求和项目说明，但不能通过修改验收规则制造成功。
2. **任务控制器**按合同运行阶段及最终验收。验收脚本启动真实程序或导入实际模块，返回 `checks / passed / failures` 和退出码；控制器保存证据并将失败诊断反馈给模型。
3. **外层 E2E**在任务结束后再次独立执行完整 CLI，检查验收脚本源码未被修改。实际使用 SDK 时，任务调用者负责提供验收合同和程序；当前未验证任意自然语言需求自动生成可靠验收标准。

金额样本要求 `--discount-bps 1000`，即折扣 10%：

| 订单 | 小计 | 正确折扣 | 正确实付 | 错误金额函数的实付 |
| --- | ---: | ---: | ---: | ---: |
| A | 4980 分 | 498 分 | 4482 分 | 4980 分 |
| B | 30 分 | 3 分 | 27 分 | 30 分 |

错误函数还会将两单折扣都写成 0。验收另检查商品名、非法数量 / 价格 / 表头和取整边界，不能只靠写出这两行金额通过完整合同。

## 5. LT-01：正常三阶段订单交付

**设计依据与合理性：**[D02：宿主验收驱动阶段与最终交付](../implemented/design-evidence.md#d02)。三阶段产物经宿主独立核查并最终复验，检验阶段推进与完整订单交付。

注册测试名：`LT-01: actual task CLI completes staged order delivery with independent evidence`

源码：[long-tasks.test.ts](../../tests/e2e/long-tasks.test.ts)。

- **初始任务：**上述存在三个问题的订单工程，阶段和验收由宿主预定义。
- **执行步骤：**宿主先运行金额验收，确认初始程序不合格；通过构建后 CLI 的 `task start` 启动真实模型任务；控制器推动三阶段及最终验收；另起 CLI 查询持久状态；宿主独立执行完整 CLI。
- **实际检查：**任务 CLI 成功退出并报告 `succeeded`；状态中三个阶段通过，全部最终验收项有当前合同版本的通过证据引用；独立完整 CLI 验收成功；可信验收脚本保持原样。
- **证明范围与边界：**证明预定义三阶段任务可以真实交付，成功状态与独立程序验收一致。主要断言关注最终结果，不要求一定出现失败修复。阶段不是 Agent 自主规划，订单样本也不代表任意大型工程。

<a id="case-06"></a>
## 6. LT-02：后续交付时依赖回归，反馈后继续修复

**设计依据与合理性：**[D02：宿主验收驱动阶段与最终交付](../implemented/design-evidence.md#d02)。已通过的折扣依赖在 CLI 阶段真实回归，失败反馈后重新修复，检验当前验收不能依赖历史通过。

注册测试名：`LT-02: model completion cannot pass corrupted output; actual model repairs verification feedback`

源码：[long-tasks.test.ts](../../tests/e2e/long-tasks.test.ts)。

- **初始任务：**与 LT-01 相同的订单工程、三个阶段和验收标准。
- **执行步骤：**通过公开 SDK 启动真实模型任务。M1、M2 验收通过后进入 M3；M3 模型片段自然结束、该阶段宿主验收尚未开始时，测试只注入一次故障，把 `calculate.mts` 覆盖为忽略折扣的错误函数。随后真实验收发现业务失败，控制器提供失败诊断，模型重新执行修复，最后宿主独立验收完整 CLI。
- **实际检查：**故障确实注入，注入时最近的模型 Run 为自然 `completed`；存在失败验收及其后的新 Run；修复继续前没有任务成功事件；最终任务 `succeeded`，独立 CLI 验收通过，验收脚本未被修改。
- **证明范围与边界：**证明在这个实际依赖回归场景中，验收门禁、失败反馈和真实模型修复能形成闭环。只注入一次缺陷，不验证持续失败后的停滞检测、任意故障分类或一般性的自我反思能力。

关键执行顺序：

```text
M1 解析 → 宿主验收通过
M2 计算 → 宿主验收通过
M3 CLI → 当前模型执行片段自然结束
宿主重新改坏 M2 的金额模块（额外故障注入）
宿主验收 → 业务失败，金额不符合合同
同一会话追加失败诊断 → 真实模型继续修复
重新验收及最终完整回归 → succeeded
```

此处仅前两阶段已经验收通过；不能写成“完整程序先通过了 M3 验收，之后才被改坏”。故障发生在 M3 阶段验收之前。忽略折扣的函数必然不满足金额合同；若 CLI 自身能避开该模块，最终全量验收仍会直接检查金额模块。失败报告包含检查数量、通过数量和实际错误；业务失败退出码为 1，完全通过为 0。本文列出的金额是合同与错误函数的确定结果，不是本次新运行日志。

### LT-01 与 LT-02 的区别

| 比较项 | LT-01 | LT-02 |
| --- | --- | --- |
| 初始工程和阶段 | 同一订单工程，M1 / M2 / M3 | 同一订单工程，M1 / M2 / M3 |
| 入口 | 实际任务 CLI | 公开 SDK，以便使用故障钩子 |
| 宿主额外注入 | 无指定回归 | M3 模型结束后，把金额模块重新改坏 |
| 必须出现的错误路径 | 未要求 | 失败验收及后续新 Run |
| 关键能力 | 正常分阶段交付和持久成功证据 | 发现依赖回归、阻止提前成功、反馈后实际修复 |

### 阶段 context 如何传递，能证明什么

两个用例各自在同一个 AgentSession 中推进，不为每个阶段创建新会话。阶段输入、模型完整回复、工具调用和工具结果保存在会话中。当前实现用 [SessionRepository.messages](../../src/storage/session.ts) 取出历史，再由 [AgentSession](../../src/harness/session.ts) 传给 [AgentRuntime](../../src/runtime/agent.ts)；没有实现阶段间上下文压缩。

发生失败后，请求内容可概括为：系统指令 + M1 / M2 / M3 的已有对话 + 当前阶段的修复提示与实际失败诊断。每个阶段提示还重复当前合同目标、约束、历史通过阶段和当前验收要求，见 [TaskController.prompt / feedback](../../src/harness/task-controller.ts)。

全部任务日志、全部验收附件不会自动原样进入模型。失败内容经过控制器转换为诊断提示；外部文件变化也不会自动改写旧对话。提示要求重新读取和复现，避免依赖旧回复推断当前代码。

这些路径说明模型可以访问前面阶段的历史，但 LT-02 没有独立观测请求投影或移除历史来验证因果关系。新提示、错误诊断和当前文件可能已足以完成修复。因此它不能单独证明“修复必须依赖早期 context”，更不能证明上下文压缩后信息仍保留；后者需要 [LT-03](engineering.md)。
