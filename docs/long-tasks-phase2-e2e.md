# 长任务第二阶段 E2E：恢复与用户控制

日期：2026-10-04。状态：**主体用例已实现，26 个 E2E 分组验收通过**。本文件保留验收规格；逐项实际结果、报告与保守兼容边界见 [第二阶段实现](long-tasks-phase2-implementation.md)。

## 1. 实际目标和测试入口

用户应能暂停一个订单工程任务，关闭进程，改变需求或修复外部条件，再从另一个进程继续完成。进程突然退出时，应保留目标与累计执行额度，先查清未完成操作和当前代码，再继续；无法查清的副作用必须明确阻塞。

第一组沿用 `tests/e2e/order-fixture.ts` 的订单任务：M1 解析、M2 计算、M3 CLI。第二组增加订单报价 HTTP 服务，避免所有设计只适用于 `src/*.mts`。

以下命令已经提供；实际平台和兼容边界见实现记录：

```text
task resume <id> --data-dir <root>
task pause <id> --command-id <uuid> --data-dir <root> --wait
task cancel <id> --command-id <uuid> --data-dir <root> --wait
task update <id> --spec <v2.json> --expected-version 1 --command-id <uuid> --data-dir <root> --wait
task command-status <id> <command-id> --data-dir <root>
```

测试使用真实 MiMo、工具和子进程。故障由宿主生命周期屏障触发，不伪造模型响应。屏障通过 IPC 告知测试进程已到达指定提交边界；宿主收到信号后终止目标执行进程，确认退出，再启动恢复进程。不得用“等待若干秒后杀进程”替代确定的故障边界。

每个用例独立创建 `.codeagent/e2e/run-*/<case>/`：`workspace/` 为实际工程，`control/` 保存不可由模型改写的合同与验收版本，`state/` 保存任务 / 会话 / 命令，`evidence/` 保存进程退出、审计、验收和结果。测试 deadline 是资源上限，超时计为失败。

## 3. LT-04：恢复实际操作，而非重复历史回复

### LT-04A：有可信回执

1. 用户任务要求调用宿主注册的 `record-delivery` 工具，登记本任务的唯一交付标记；宿主验收也要求存在此标记，确保真实模型必须调用该工具。工具声明 `replay: never`。
2. 工具向工作区外的测试审计文件追加标记并同步，保存包含 `operationId / callId / receiptHash` 的回执。重复执行会再次追加，不用工具自身去重掩盖 Harness 的重放错误。
3. 在“副作用与回执已落盘、会话 tool_result 尚未提交”的屏障强制终止执行进程。
4. 新进程从公开 `task resume` 进入。只读恢复适配器按原 operation ID 查询回执，提交恢复结论，补齐原工具调用的结果，再重验当前工程。
5. 真实模型继续未完成阶段，宿主独立执行整个订单 CLI。

关键断言：审计标记只有一次；恢复结论引用匹配原调用的回执；最终 JSON 正确；原 task / session 身份及累计 Run、repair 用量保留。唯一效果数量属于业务契约，不固定模型其他工具的次数。

### LT-04B：结果不可确认

使用同一故障边界，但查询适配器返回 `unknown`。要求恢复进程在调用后续模型和有副作用工具前进入 `blocked: effect_unknown`，保留原调用和缺失证据。随后宿主使回执可查询，显式 resume 才可继续。

验收检查真实审计文件和请求 / 工具启动记录，不能只检查阻塞提示文本。默认 shell 无可靠回执时也采用这一策略；文件内容符合预期不能证明任意命令的全部副作用已经确认。

### LT-04C：任务日志与会话日志交接

分别在以下屏障终止进程：Run 计划已提交但输入未接收；会话输入已接收但任务应用记录未提交；会话 Run 已结算但任务 Run 结果未提交。

恢复必须按稳定 ID 和内容摘要对账，而非按相似文本或时间猜测。已接收输入不能重新追加；缺失的任务引用可以补交；中断的执行片段保留已占用额度，新的恢复片段另计额度。额外验证“同 ID、不同内容”被拒绝。

本用例只证明输入交接和既有 Run / repair 额度不重置。模型请求 / token / 活动时间的全局预留仍由 LT-05 单独验证。

### LT-04F：默认文件工具

在真实模型 write 工具写入指定实现文件后、结果提交前强退。intent 必须保留预期内容摘要和工具版本；恢复适配器只读当前文件，确认单文件后置条件已满足，记录“当前状态已核对”，不能把它伪称为原操作的完整执行回执。恢复不重放原调用，继续后最终独立验收通过。

增加摘要不匹配且无法确认工具影响范围的变体，要求阻塞而非宣称原写入成功。这样有回执的自定义工具不能替代默认编码工具的恢复验证。

### LT-04D / E：验收与旧日志

- 验收附件已同步但没有对应通过事件：恢复忽略孤立附件的通过结论，重新执行可信验收，取得当前指纹和已提交证据后才能成功。
- `snapshot.json` 丢失或过期：从权威日志恢复相同已提交事实，不凭缓存增加通过阶段。
- 日志末尾只有半条记录：独占写权限后备份原文件，修复明确的不完整尾部，保留此前提交事实。
- 中间记录损坏、序号异常或未来 schema：拒绝执行，不截断中间历史后继续。
- 第一阶段 v1 的已结束任务：仍可查询历史结果；缺少稳定输入关联或进程身份的活动旧任务，返回明确的迁移阻塞，不推断为可安全续跑。保留原始文件。

## 4. LT-07：旧通过证据不代表新任务已经完成

### LT-07A：更新需求

在 M2 已验证、M3 尚未启动的安全边界暂停。宿主准备完整 v2 合同，折扣改为 2000 bps；v2 验收文件单独保存，不能改写 v1 验收文件。通过 update 命令提交 `expectedVersion=1` 和唯一 command ID。

同一命令重复投递应返回同一结果，只产生一次版本更新；同 ID 携带不同内容应冲突；不同 ID 携带过期 expectedVersion 应冲突。真实恢复执行最终应交付：A `4980 / 996 / 3984`，B `30 / 6 / 24`。

关键断言：当前版本为 2；最终所有证据绑定 v2 及当前指纹；预算用量未被版本更新清零；旧证据仍可追查但不能直接授权成功。暂停期间 update 仅改变合同，直到显式 resume 才启动模型。

### LT-07B：工作区变化

暂停后由宿主把计算模块改坏，再 resume。需求版本不变，但内容指纹变化，旧证据必须失效。真实模型修复后全量验收通过。以未受模型回复影响的源码、输出和验收结果断言能力。

## 5. LT-08：控制请求必须落实到真实状态

### LT-08A：暂停

在活动工具期间投递 pause。未到安全边界时只允许报告 queued / pending；当前工具批次提交完、托管进程退出后才提交 paused 收据。paused 后不发出新的模型请求或工具调用。关闭执行进程，启动新进程 resume，目标、合同、证据和累计额度保持，最终交付正确。

CLI `--wait` 超时只说明收据尚未返回，不能将其解释为暂停成功或撤销已发布命令。命令状态可独立查询，测试不靠固定等待时间猜测生效。

### LT-08B：取消与残留进程

宿主准备一个前台父子进程工具，通过 IPC / 心跳文件证明子进程正在运行，再从另一 CLI 投递 cancel。先等待命令接收事实，再检查进程组停止、心跳停止、cancelled 结果及后续动作停止。重新启动执行入口不得重放未结束的工具或自动继续已取消任务。

额外在执行者强退后检查子进程清理；恢复在确认旧进程组静止前不能验收工作区。强退没有取消命令时仍属于中断，不自动写成用户取消。

### LT-08C：竞争和平台边界

同步释放两个恢复进程，要求只有一个获得写入执行权；另一个返回 busy，不调用模型。重复检查存活所有者的元数据年龄很大时仍不能接管。原执行者强退后，新进程通过操作系统锁获得执行权，完成旧进程清理与状态对账后才继续。

增加两个 Task 指向同一规范工作区、状态目录不同但使用相同执行权注册目录的变体，禁止并发修改。Windows 原生后端缺失、进程组归属无法确认、旧格式锁身份不明时必须阻塞，不能降级为按 PID 或锁年龄删除文件。首批实际平台为本机 Windows / 本地文件系统，不宣称其他平台已经验证。

### LT-08D：成功提交竞争

在“最终验收通过、成功尚未提交”屏障分别发布 update 和 cancel，收到 durable 发布收据后放行。要求 update 导致新版本重新验收，cancel 导致 cancelled；旧版本不得先变成成功。

再测试成功已经提交后才发布命令：返回 terminal_task 拒绝收据，保留成功历史。顺序由控制发布与成功提交共用的短临界区确定，不以墙钟时间判断先后。

## 6. LT-10：跨工程结构验证

新增无 `src` 目录的 TypeScript 报价服务：`lib/quote.mts` 计算订单金额，`app/server.mts` 提供 `POST /quote`；只依赖 Node 内置模块，端口由宿主选择空闲端口或由监听 0 返回实际端口。

公开合同要求有效 JSON 请求返回正确报价，非法数量返回 400；进程每次启动后仍能读取相同持久配置。宿主 HTTP 客户端真实发请求，不能把函数单测替代服务验收。M1 完成金额逻辑后暂停，跨进程恢复并完成 HTTP 入口；最终验证报价、非法请求和服务重启。

任务声明可修改路径 `app / lib`，不创建 `src`。关键断言是有效 HTTP 结果、进程清理、恢复身份及当前证据。若控制器要求写入 `src`、重建订单 CLI 或修改宿主验收才能通过，用例失败。

## 7. 交付门槛与诊断

所有恢复成功变体都从真实模型执行到独立验收；阻塞 / 取消变体检查实际未发生的后续请求与副作用。日志同时保存 task ID、schema / 合同版本、原与恢复执行者身份、故障屏障、命令 ID 和结果、累计额度、操作回执摘要、模型公开配置、工作区及独立验收路径，不记录密钥。

第二阶段还必须落实 LT-09 的两个恢复边界：验收进程不可用时 blocked、不虚报通过；任务或会话的必要持久写入失败时，停止后续模型 / 工具启动并报告未提交，不能假称停止状态已落盘。

建议新增 `tests/e2e/task-recovery.test.ts`、`task-control.test.ts`、`quote-service-fixture.ts`。先让用例因缺少公开接口或必要行为而失败，再实现；单元测试只补充输入去重、恢复分类、合法状态转换及命令处理的确定性不变量。LT-01 / LT-02 和原有 4 个 E2E 继续作为回归门槛。

规格不等于通过证据。实际执行见实现记录，各次失败与重跑报告保留，尚未覆盖的变体明确标注。
