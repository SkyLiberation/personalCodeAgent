# 长任务 E2E 用例设计

日期：2026-10-04。状态：**LT-01 / LT-02 及 LT-04 / LT-07 / LT-08 / LT-10 主体用例已验证**；LT-09 恢复相关故障也已覆盖。LT-03 / LT-05 / LT-06 与完整 LT-09 留待后续。第二阶段细分规格见 [恢复与控制 E2E](long-tasks-phase2-e2e.md)，26 个分组通过记录见 [第二阶段实现](long-tasks-phase2-implementation.md)。

本文件先定义真实任务和验收，再由 [长任务处理方案](long-tasks.md) 推导架构。现有 [4 个 CLI E2E 用例](e2e.md) 是短任务基线，不能证明本文全部长任务能力。第一阶段已提供任务 start / status 与 SDK 验收故障屏障，其余入口和能力以对应实施状态为准。

## 1. 验证目标与执行约束

长任务指跨多个执行阶段、可能超过单次上下文或进程生命周期，且需要保留目标与验收证据的任务。测试通过缩小上下文预算、设置阶段边界和注入真实进程故障，在有限时间内触发这些条件；不依赖让模型闲聊数小时。

- 从真实 CLI 或公开 SDK 进入，使用真实 MiMo 模型、真实文件工具和真实子进程；不使用 FakeGateway 代替模型完成任务。
- 沿用 `tests/e2e/helpers.ts` 的独立工作区、会话目录、日志脱敏和子进程清理方式。运行配置记录模型、公开 base URL 和有效预算，不记录 API Key。
- 故障控制仅改变执行环境、子进程或持久化提交时机，不伪造模型成功回复。可控制的 SDK 生命周期钩子只能用于测试，不开放为模型工具。
- 验收由测试宿主独立执行。验收脚本、任务定义和原始输入副本位于工作区外，供 Agent 阅读的需求副本不能修改真正的验收规则。
- 仅断言关键任务结果、恢复语义和资源边界；不固定代码风格、回复措辞、模型轮次、摘要文本或内部调用顺序。
- 任一模型 API、测试基础设施或日志存储故障都须记录失败原因；不能将跳过、缺少验收结果或模型自述标记为通过。

## 2. 共用实际任务：订单处理 CLI

### 2.1 初始环境

每次执行创建新的 `run-*` 根目录。建议沿用 `.codeagent/e2e/run-*/`，用例内分为：

```text
<run-root>/<case-id>/
  workspace/                  Agent 的目标工作区
    AGENTS.md                 UTF-8、金额使用整数分等项目约束
    src/parse.mts             有缺陷或未完成的 CSV 解析
    src/calculate.mts         有缺陷或未完成的订单汇总
    src/cli.mts               有缺陷或未完成的 CLI
    data/orders.csv           输入数据
  control/                    测试宿主持有的需求、预算和验收脚本
  state/                      任务、会话和执行日志
  evidence/                   独立执行结果、故障记录和最终报告
```

这里的目录区分是测试职责划分。当前本地 shell 具有主机权限，目录位于工作区外不构成操作系统安全隔离。测试宿主应检查验收文件及输入副本的摘要；若被修改，用例失败。真正隔离应由后续执行环境后端提供。

### 2.2 用户任务与真实链路

用户要求：“完善订单处理 CLI，支持 CSV 引号与中文字段、整数分金额计算、折扣和稳定 JSON 导出；每个阶段完成后运行对应验收，最终运行整个 CLI。”

执行入口：

```text
node src/cli.mts --input data/orders.csv --discount-bps 1000 --output out/summary.json
```

输入 CSV 字段为 `order_id,sku,quantity,unit_price`，样例至少包含：

| order_id | sku | quantity | unit_price |
| --- | --- | --- | --- |
| A | A,1（CSV 中使用双引号包裹） | 2 | 19.90 |
| A | B | 1 | 10.00 |
| B | 中文商品 | 3 | 0.10 |

折扣以订单小计计算：`discountCents = floor(subtotalCents * discountBps / 10000)`；`totalCents = subtotalCents - discountCents`。A 应为 `4980 / 498 / 4482`，B 应为 `30 / 3 / 27`。订单按 ID 排序；商品字段不得损坏；非法数量或价格返回非零退出码，不输出成功结果。

三个阶段的验收合同分别是：M1 正确解析有效输入并拒绝非法输入；M2 正确计算数量、整数分与折扣；M3 从真实 CLI 得到满足合同的文件并通过完整回归。阶段名称和划分可以调整，但验收能力不得因模型的计划而减少。

验收脚本从工作区导入模块或启动 CLI，使用宿主持有的有效、非法和金额边界样本。测试先确认初始代码不满足合同；Agent 执行后，宿主再次独立验证。验收进程须移除继承的 `NODE_TEST_CONTEXT`，避免嵌套 `node --test` 未真正执行测试。

## 3. 必须落实的用例

| ID | 场景 | 核心能力 |
| --- | --- | --- |
| LT-01 | 多阶段订单任务完整交付 | 分阶段工作与最终独立验收 |
| LT-02 | 模型结束但产物不满足合同 | 阻止虚假完成、验收反馈继续修复 |
| LT-03 | 上下文压力下继续完成任务 | 目标保留、摘要恢复、协议完整 |
| LT-04 | 写入后、结果提交前强制退出 | 跨进程恢复与不确定副作用处理 |
| LT-05 | 多次恢复仍受同一预算限制 | 全任务预算累计与可靠停止 |
| LT-06 | 持续得到同一失败结果 | 无进展检测、有限重规划与阻塞报告 |
| LT-07 | 恢复前变更需求或工作区 | 需求版本、验收失效与重新验证 |
| LT-08 | 停止请求、并发恢复与陈旧锁 | 可取消、单一执行者与安全接管 |
| LT-09 | 验收或日志基础设施故障 | 区分任务错误与基础设施错误，提交失败时停止 |
| LT-10 | 不同目录结构的报价 HTTP 服务 | 通用控制器不依赖订单 CLI / src，暂停恢复后真实服务正确 |

### LT-01：多阶段完整交付

1. 创建共用订单工作区和可信验收合同，确认初始验收失败。
2. 从任务 CLI/SDK 创建任务，真实模型经 Agent loop 读代码、修改代码、运行程序。
3. 各阶段通过后推进；最终宿主重新运行全量验收和真实 CLI。

关键断言：输出满足第 2 节合同；最终任务为 `succeeded`，且有绑定当前需求版本与工作区版本的全量验收证据；可信验收脚本未被改动。允许一个模型执行片段完成多个阶段，不断言固定轮次。

### LT-02：结束声明不等于验收通过

在 M3 的模型执行片段自然结束、完整验收尚未开始的边界，通过测试生命周期钩子把 `calculate.mts` 的折扣逻辑重新改坏，确保验收必然失败；保留真实模型输出。只注入一次。

关键断言：失败证据提交后，任务没有进入 `succeeded`；失败信息进入后续真实模型请求，Agent 修复后最终独立验收通过。若有限修复预算耗尽，必须以未完成状态结束并明确缺失项，不能算该修复能力用例通过。

失败反馈应包含实际复现命令与关键结果，旧阶段通过仅代表历史快照。宿主状态目录不是工作区文件工具的可读路径，不能只给模型一个无法读取的证据文件地址。

### LT-03：上下文压缩后目标仍有效

在初始用户输入中加入随机 `runLabel`，要求最终 JSON 携带该值；它不写入工作区的需求副本。在已提交工具批次的边界，测试宿主通过 SDK 注入来自真实诊断文件的上下文材料，并设置足以保留必要内容、但要求压缩旧前缀的软阈值。材料与阈值由宿主控制，不依赖模型碰巧读取足够大的日志。

关键断言：确实发生上下文压缩；最终文件携带正确 `runLabel` 并通过订单合同；原始历史仍可读取；真实模型请求没有孤立的工具结果，也没有丢弃保留区间内的原生 assistant 协议数据。验证这些协议不变量，不断言摘要字句或精确 token 数。

压缩阈值可在测试中调低，但不能低于当前请求的必要内容。若必要内容已超容量，应明确返回 `context_capacity_exceeded`，另以该边界变体验证，不能静默丢掉用户约束。

### LT-04：中断恢复与未知副作用

详细屏障、输入交接、默认文件工具及旧日志变体见 [第二阶段 LT-04 规格](long-tasks-phase2-e2e.md)。

准备一个额外 SDK 测试工具：向宿主持有的审计文件追加唯一操作标记，声明 `replay: never`。真实模型发起调用后，测试在工具副作用完成、工具结果尚未持久化的提交边界强制终止进程。故障时机由测试屏障控制，不能仅依赖时间延迟。

启动新进程恢复同一任务、工作区和会话；控制器先读取审计标记、检查实际文件，并补齐中断的工具结果，再决定后续动作。该工具在测试中允许宿主按操作 ID 查询结果；默认编码工具仍不能获得这个幂等保证。

关键断言：跨进程保留已提交阶段、目标和预算；审计标记只出现一次；没有盲目重放原调用；恢复后订单任务通过最终验收。再增加工具无查询能力的变体，要求任务停在 `blocked` 并报告未知副作用，不能假定操作未发生。

### LT-05：预算不可通过恢复重置

为任务设置较小的全局模型请求次数预算，在安全边界停止并跨进程恢复至少一次。执行片段可以有各自轮次上限，但不能覆盖全局限制。摘要和自动重试也计入模型请求次数。

关键断言：各进程累计实际发出的模型请求未超过合同预算；到达上限后没有新的模型请求或工具启动；任务为 `budget_exhausted` 且记录已用量、剩余事项和最近证据。使用次数断言是因为预算本身就是公开能力，不断言某个任务必须恰好耗费几次请求。

变体：请求已发出、usage 未返回即退出；恢复后该请求仍占用一次额度，token/cost 标记为未知或保留预留额，不能按零用量继续无限运行。

### LT-06：无进展时有限重规划

主变体沿用 LT-02 的受控边界，但在 M2 每个修复片段结束、验收开始前持续恢复同一个折扣缺陷，模拟外部过程反复覆盖文件。真实验收因此反复得到同一个业务失败；代码编辑本身不能冒充阶段进展。

关键断言：控制器在配置的无进展窗口与重规划额度内停止继续调用；任务为 `blocked: no_progress`，保留重复失败证据及已尝试策略；不伪造合格结果。另一个变体停止覆盖，让模型真正通过新阶段，确认有效进展不会被误判为停滞。

缺失输入变体：提供“必须使用指定汇率文件”的要求，而文件不存在且禁止编造汇率；要求输出可解释的阻塞原因。该变体验证缺少输入的停止行为，不单独充当无进展检测已经执行的证明。

### LT-07：需求或文件变化使旧证据失效

完整新合同、命令去重、暂停状态更新及金额验收见 [第二阶段 LT-07 规格](long-tasks-phase2-e2e.md)。

M2 验收通过后暂停任务。宿主可选择一种变化：提交带唯一输入 ID 的新用户需求（折扣从 1000 改为 2000 bps）；或者直接修改 `calculate.mts` 造成回归。重启并恢复同一任务。

关键断言：新需求持久化为新版本，重复输入 ID 不重复应用；受影响阶段的旧证据失效；按新合同或新文件状态重新验证，最终输出正确。已通过的旧测试不能直接授权新版本任务完成。

### LT-08：停止、并发执行和锁接管

暂停、取消、真实子进程、工作区竞争及成功提交竞争见 [第二阶段 LT-08 规格](long-tasks-phase2-e2e.md)。新方案使用操作系统执行权，旧 PID 文件锁的迁移必须核实原进程退出，不能按锁年龄接管。

在受控、尚未产生业务副作用的等待型工具运行时，通过公开任务入口停止任务；另一个进程同时尝试恢复。随后分别测试原进程活着、原进程确已退出两种锁情况。

关键断言：停止请求已持久化；子进程被终止，停止后不启动新工具；任务进入 `cancelled`，不会因重启自动续跑。两个进程不能同时执行同一任务；存活进程的锁不能因年龄被窃取；确认所有者已退出后才允许接管并重新检查工作区。

强制终止造成的锁残留属于进程中断，不自动等同用户取消。对 PID 身份无法确认的情况，返回可诊断的冲突状态。

### LT-09：验收与提交失败不能变成成功

变体 A：在阶段验收进程启动前，使验收器依赖的宿主资源不可用。变体 B：在模型请求或工具意图提交前，由测试存储包装器注入一次实际写入失败。包装器仅让真实存储失败，不提供替代成功记录。

关键断言：A 的结果为 `verification_unavailable`，不能解释为代码已经通过或要求模型修改正确代码；B 在相应外部动作发生前停止，不能在日志失效后继续调用模型或执行新工具。宿主恢复资源后显式恢复任务，应重新获取缺失证据。

### LT-10：跨工程结构验证

增加没有 `src` 目录的 `app/` + `lib/` 报价 HTTP 服务，从真实 SDK / CLI 暂停后跨进程恢复。独立 HTTP 客户端检查有效报价、非法请求和服务重启；路径、阶段及验收由宿主合同提供。详细任务和验收见 [第二阶段 LT-10](long-tasks-phase2-e2e.md#6-lt-10跨工程结构验证)。此用例尚未实现 / 执行，不能替代现有订单用例的实际通过记录。

## 4. 结果记录与实施入口

测试文件为 `tests/e2e/long-tasks.test.ts`，通过真实任务 CLI 执行 LT-01，通过公开任务 SDK 和真实模型执行 LT-02。二者已纳入 `pnpm test:e2e`；该命令现在运行 4 个短任务和 2 个长任务用例，尚不包含 LT-03 至 LT-10。

每个用例的报告至少保存任务 ID、需求版本、工作区路径、模型配置、有效预算、实际结果、独立验收输出路径和终止原因。故障用例额外保存注入边界、进程 ID 与恢复结果。`succeeded` 必须能追溯到对应验收记录；诊断日志中的敏感值按现有规则脱敏。

实施顺序：先 LT-01 / LT-02 建立任务与验收闭环，再按 [第二阶段方案](long-tasks-phase2.md) 用 LT-04 / LT-07 / LT-08 建立恢复语义，并以 LT-10 检查通用性；随后 LT-03、LT-05、LT-06、完整 LT-09 完成上下文与控制边界。每一步只在真实 E2E 通过后声明相应能力已实现。
